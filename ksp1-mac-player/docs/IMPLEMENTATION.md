# Implementation architecture

## Clean separation

`ksp1_runtime` owns all container concerns:

1. reads the complete KSP file into bounded host memory;
2. validates the header, table dimensions, file ranges and CRCs;
3. parses engines, pages, tracks, resources and UTF-8 strings;
4. decodes ZX0 and block containers;
5. reconstructs exactly one requested runtime page;
6. checks the final page CRC;
7. creates a temporary KSCC image for libkss.

`ksp1player` owns only desktop playback:

1. selects a public 16-bit track;
2. asks `ksp1_runtime` for its reconstructed KSCC image;
3. converts that image through `KSS_bin2kss`;
4. runs it through `KSSPLAY`;
5. sends signed 16-bit PCM to SDL2;
6. handles public next/previous navigation;
7. handles ABI-1 dynamic page requests;
8. routes writes to two independent SCC emulators when a dual-SCC ABI is detected;
9. displays rendered playback time and applies interactive per-channel SCC masks;
10. reconstructs complete emulator state for safe timestamp seeking.

No game name, filename, legacy KCP variant or private pack identifier appears in the playback decisions.

## Page encodings

### Sparse overlay

The engine template is decoded once and copied. Ordered sparse records replace byte ranges.

### Complete page

The page payload directly decodes to the complete engine page.

### Shared block map

A `PBM1` map references fixed-size logical blocks from a `PBK1` resource. Slabs are independently decoded and the requested block slice is copied into the page.

### Resource map

An `RMP1` map copies arbitrary ranges from decoded package resources and supports inline literals and fills.

### Hybrid pool

`HPL1` is decoded into a unified desktop block pool. The RAM/VRAM/cold tier declarations remain available for the future MSX implementation but do not constrain host memory placement. A page row maps every destination position to one pooled block.

## Dynamic page switching

For engines carrying `KSP_ENGINE_DYNAMIC_PAGES`, the player installs an ABI-1-compatible gateway:

- engines with at most 256 local pages submit the low byte through `A` and a zero high byte;
- larger engines submit the full index through `HL`.

ABI 1 requires `A` to mirror the low byte of `HL`, so the first form is identical for conforming small engines. It also accepts early converters such as the ESCHATOS N163 engine, which supplied the correct page in `A` but retained an unrelated working pointer in `HL`.

The libkss memory-write hook collects the engine-local page index, materializes the corresponding global page, and replaces only `replace_start..page_end`.

The current implementation performs materialization synchronously in that callback. It is functionally correct for testing. A production low-latency revision should enqueue the page number and perform allocation/decompression at a safe audio boundary.


## Dual-SCC desktop bridge

The player keeps libkss's normal SCC as cartridge A and creates a second
`emu2212` SCC as cartridge B. The Z80 engine selects which cartridge owns the
SCC register window; writes for B are intercepted by the memory-write hook and
sent only to the second emulator. Both SCC clocks continue between selections
and their PCM outputs are mixed at each rendered sample.

Two callback layouts are supported:

- native KSP1 dual SCC: `D900` selects A, `D904` selects B and `D908` disables
  the cartridge window; normal dynamic pages continue through the engine's
  declared gateway, normally `D8A0`;
- early compatibility layout: `D900` submits an 8-bit page number and `D903`
  selects A/B from register A. This is recognized from the engine bytecode and
  translated at load time, even when the old package omitted the dual-SCC flag.

The callback stubs are appended to the temporary KSCC load image before
`KSSPLAY_reset`, so engine INIT writes use the same routing as PLAY writes.
No game title or filename is consulted.


## Playback clock and channel isolation

The live clock reads `AudioState.rendered_frames` while the SDL audio device is
locked and divides it by the configured sample rate. It therefore reflects PCM
frames actually generated by the callback rather than elapsed wall-clock time.
The terminal line is redrawn only when the whole-second value changes or a
channel key is pressed.

Keys `1` through `5` control channels 1 through 5 of SCC A. Keys `6`, `7`, `8`,
`9`, and `0` control channels 1 through 5 of SCC B. A five-bit mute mask is kept
for each cartridge:

- SCC A is updated through `KSSPLAY_set_channel_mask`;
- SCC B is updated through `SCC_setMask` on the independent emulator.

Mask changes occur while the SDL audio device is locked. Register writes and
oscillator state continue while muted, so unmuting resumes the current musical
state rather than restarting the channel.

## Safe seeking

Seeking never edits a driver song pointer or advances only the public clock.
While the SDL audio device is locked, the player resets the selected KSS song,
resets the external SCC-B emulator and dual-SCC routing mailboxes, reapplies the
current channel masks, and renders audio into a discard buffer up to the target
frame. This executes INIT and every PLAY tick in order, including dynamic page
requests and cartridge-selection callbacks.

The resulting state is equivalent to uninterrupted playback at that timestamp,
including libkss filter history and the phase of both SCC emulators. Backward
and forward seeking use the same reconstruction path for determinism. After a
seek, loop-count fading is rebased at the new position so a previously crossed
loop does not cause an immediate fade; the absolute track-duration fade remains
in effect.

Controls are Up/Down or `[`/`]` for ten seconds and `{`/`}` for sixty seconds.
Because dual-SCC output is mixed sample-by-sample, long seeks may pause briefly
while the state is reconstructed.

## KSCC bridge

libkss consumes KSS/KSCC rather than KSP directly. The bridge uses the selected page as one KSCC load image and copies the engine's load, INIT and PLAY addresses. PSG/SCC use the normal MSX baseline; YM2413 and Y8950 are represented by their KSCC device flags.

For a KSP 1.01 engine carrying `KSP_ENGINE_PAGE2_RUNTIME`, the bridge duplicates
the reconstructed 4000h-7FFFh page into 8000h-BFFFh in the initial KSCC image.
It also sets KSCC device bit 2; in MSX mode libkss interprets that bit as
writable RAM, which the engine's mutable page-2 runtime area requires. This is
selected entirely by package metadata and contains no game-specific detection.

`KSP_ENGINE_PAGE3_WORKRAM` needs no bridge payload expansion on desktop hosts:
the KSS runtime already supplies an isolated writable 64 KiB address space.
Native DOS players use the flag to map private page 3 only around INIT, PLAY,
and STOP calls.

This bridge is regenerated when changing public tracks, allowing tracks to select another engine or page without extending libkss's file parser.

## Deliberate future work

The KSP parser already exposes all resources, but these playback integrations remain separate work:

- MWK upload and MoonSound backend creation;
- mapper callbacks for live BNK8/BN16 engines;
- SCREEN 5 images and UTF-8/Japanese UI rendering;
- asynchronous dynamic-page request queue;
- a native macOS graphical front end.
