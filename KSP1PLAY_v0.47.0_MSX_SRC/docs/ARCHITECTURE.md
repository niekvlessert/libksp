# Architecture

## 1. Main player

`src/KSPPLAYER.asm` is an ordered manifest. It contains no implementation logic;
the order of its includes defines the fixed `0100h..77FFh` player image.

### Core

- `core/startup_io.asm` — entry point, DOS1 FCB helpers and application defaults.
- `core/mapper_kspos.asm` — mapper API discovery, page ownership and KSPOS setup.

### Package format

- `format/ksp_format.asm` — KSP header/table validation and format-level helpers.
- `data/package_workspaces.asm` — in-RAM header/engine/track/page/resource records.
- `include/ksp_format.inc` — record sizes, offsets, flags and type constants.

### Runtime

- `runtime/track_engine.asm` — logical track resolution, page preparation and install.
- `runtime/engine_calls_audio.asm` — track stepping and engine/audio call paths.
- `runtime/stream_decode.asm` — ZX0-style stream input/output and mapped history.
- `runtime/compat_helpers.asm` — dynamic-page gateway and compatibility helpers.
- `runtime/RECON_RUNTIME.asm` — page-materialization runtime executing at `C400h`.
- runtime-image files — fixed host images copied to their execution addresses.

### Platform

- `platform/vdp.asm` — V9938/V9958 register, VRAM and timing helpers.
- `platform/hardware.asm` — hardware capability and SCC/SCC+ slot detection.
- `platform/runtime_audio.asm` — runtime device checks and audio setup.

### UI

- `ui/application.asm` — top-level browser/playback state machine.
- `ui/package_loader.asm` — package open/validation/preparation.
- `ui/track_browser.asm` — track navigation and selected-track transitions.
- `ui/input.asm` — keyboard capture and logical action mapping.
- `ui/text_layout.asm`, `ui/text_renderer.asm` — 80-column text presentation.
- `ui/metadata_playback.asm` — metadata pages and elapsed/total time.
- `ui/overlay_loader.asm` — logo/menu/runtime-image loading.
- `ui/game_intro.asm` — game presentation and page-3 UI setup.
- `ui/menu_backend.asm` — bridge between player and `KSPMENU.BIN`.
- `ui/KSPMENU.asm` — reloadable menu/rendering module at `8000h`.

### State

- `data/player_state.asm` — long-lived player, stream and mapper state.
- `data/ui_state.asm` — UI/browser/playback presentation state.

## 2. Cross-runtime interfaces

The project deliberately separates address constants by owner:

- `menu_abi.inc` — KSPMENU public entry/data addresses.
- `recon_abi.inc` — page-materialization runtime jump table.
- `service_abi.inc` / `service_runtime_abi.inc` — service runtime calls/data.
- `hvar_abi.inc` / `hvar_format.inc` — HVAR runtime and shared state.
- `ui_p3_abi.inc` — page-3 playback helper jump slots and implementations.
- `kspos_abi.inc` / `kspos_runtime_abi.inc` — KSPOS gateway/shared state.
- `memory_map.inc` — fixed sizes and regions, not callable semantics.

A numeric address should not be used as a substitute for these interfaces.

## 3. Generated source

`build.py` assembles `runtime/RECON_RUNTIME.asm` for runtime origin `C400h`, verifies
its fixed image, and emits `src/generated/RECON_RUNTIME_IMAGE.inc`. The main player
includes that generated byte image in its host slot. Edit the readable runtime,
not the generated include.

## 4. Why the source has host and runtime addresses

Several routines are stored inside the fixed player image but execute after being
copied to another CPU address. Consequently:

- a **host address** answers “where are these bytes stored in KSPPLAYER?”;
- a **runtime address** answers “where does this routine execute/call from?”;
- an **ABI symbol** answers “what operation/state does this address represent?”.

Keep all three concepts distinct.
